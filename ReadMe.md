# Лабораторная работа №3

## Разработка testbench на языке Verilog

### Цель работы

Целью лабораторной работы является получение практических навыков разработки
тестовых окружений для цифровых устройств на языке Verilog HDL и проверки
работы нескольких разнотипных блоков в процессе моделирования.

В ходе выполнения работы необходимо:

- освоить разработку testbench для уже готовых Verilog-модулей;
- получить практический опыт формирования тестовых воздействий на входах DUT;
- научиться синхронизировать стимулы с тактовым сигналом;
- освоить использование `wait` для ожидания событий, формируемых проверяемым модулем;
- научиться работать с системной переменной `$time` для фиксации момента
  получения результата;
- освоить работу с задержками `#...` и директивой `` `timescale ``;
- научиться выполнять последовательность тестов для счётчика, ПЗУ, ОЗУ и АЛУ;
- научиться анализировать результаты моделирования и временные диаграммы;
- получить опыт взаимодействия собственного testbench с внешним опорным
  testbench.

### Общая постановка задачи

В рамках лабораторной работы проверяются четыре уже готовых цифровых блока:

- счётчик (`Counter`);
- постоянное запоминающее устройство (`ROM`);
- оперативное запоминающее устройство (`RAM`);
- арифметико-логическое устройство (`ALU`).

Код проверяемых устройств предоставляется в файле `blocks_dut.v`.
Разрабатывать или изменять эти модули не требуется.

Задача студента состоит в разработке собственного модуля `top_1`,
который формирует необходимые входные воздействия, ожидает результаты работы
проверяемых блоков и передаёт результаты проверки во внешний опорный
testbench.

Опорный testbench предоставляется преподавателем. Он подключает
`top_1` и собственный эталонный testbench к независимым экземплярам
тех же DUT и автоматически сравнивает результаты их работы.

Таким образом, в данной лабораторной работе проверяется не только наличие
правильных конечных значений, но и **правильность временной организации
тестовых воздействий**.

# Порядок выполнения работы

## 1. Получить индивидуальный вариант

Индивидуальный вариант уже выдан студенту и размещён в соответствующем
проекте на GitLab.

Параметры варианта — значения счётчика, размер ПЗУ, набор тестов ОЗУ,
операции и тестовые векторы АЛУ, а также параметры `timescale` — уже заданы.
Самостоятельно выбирать значения варианта не требуется.

## 2. Получить проект с GitLab

Необходимо клонировать выданный проект с GitLab на свой компьютер.

После получения проекта следует ознакомиться с его структурой и определить:

- файл `blocks_dut.v` с готовыми проверяемыми модулями;
- файл, в котором необходимо реализовать `top_1`;
- предоставленный опорный testbench;
- файлы и скрипты, необходимые для запуска моделирования.

## 3. Разработать `top_1`

Необходимо реализовать модуль `top_1` в соответствии с заданным
интерфейсом и требованиями лабораторной работы.

Интерфейс `top_1` изменять нельзя: имена и разрядности портов
зафиксированы и используются опорным testbench.

Для каждого из четырёх блоков необходимо сформировать требуемые тестовые
воздействия, дождаться результата и передать его через соответствующую пару
выходов `<блок>_result_o` и `<блок>_timestamp_o`.

## 4. Запустить моделирование

После реализации `top_1` необходимо запустить предоставленный
опорный testbench.

При корректной реализации опорный testbench должен подтвердить соответствие
результатов собственного тестового окружения и `top_1`.

Необходимо убедиться, что моделирование выполняется без ошибок.

## 5. Проверить временное поведение

Особое внимание необходимо уделить временной организации стимулов.

В GTKWave необходимо проверить:

- моменты изменения входных сигналов DUT;
- их привязку к фронтам `clk`;
- длительность управляющих импульсов;
- моменты появления сигналов готовности;
- момент фиксации результата;
- соответствие сохранённого `$time` моменту получения результата.

Отдельно необходимо проверить, что значение `` `timescale `` соответствует
значению, заданному для варианта. Ошибка в единицах времени приводит к
смещению стимулов относительно тактового сигнала и может сделать
моделирование некорректным.

## 6. Зафиксировать результаты

В отчёте необходимо привести результаты моделирования и скриншоты
временных диаграмм GTKWave, подтверждающие корректную работу
`top_1`.

**Проверка синтезируемости в рамках данной лабораторной работы не выполняется.**

## Общие требования к реализации

1. Реализовать только собственный testbench `top_1`.
2. Соблюдать точный интерфейс `top_1`, заданный в проекте.
3. Использовать значения индивидуального варианта, предоставленные в проекте.
4. Все тестовые воздействия формировать в соответствии с указанными в задании
   тактами и задержками.
5. Для ожидания событий от DUT использовать `wait`, если это предусмотрено
   конкретным заданием.
6. Моменты фиксации результатов записывать через `$time`.
7. Результаты передавать через соответствующие выходы `result_o` и
   `timestamp_o`.
8. Не изменять опорный testbench с целью обхода или отключения проверки.
9. Проверить работу всех четырёх блоков: Counter, ROM, RAM и ALU.

Для каждого блока нужно выставить пару выходов `<блок>_result_o` (16 бит) и
`<блок>_timestamp_o` (64 бита, значение `$time` в момент фиксации
результата).

## Timescale

Тактовый сигнал `clk` генерируется опорным testbench-ом с периодом
**10** единиц времени (фронты приходятся на моменты
t = 5, ... с шагом 10).

В качестве единиц времени задать: 1us, в качестве точности задать: 1ns.

Это значение сгенерировано для вашего варианта и нигде за вас не
подставляется. Если вы укажете **другое** значение
(или не укажете вовсе), все ваши `#...`-задержки будут отсчитываться в
других реальных единицах времени, чем у опорного
testbench-а — стимулы разойдутся по времени с тактовым сигналом, и
проверка не пройдёт, даже если логика верна.

# Блок 1. Счётчик (Counter)

## Задание

Модуль `counter_dut` считает такты от 0 до N. Нужно на заданном такте подать
на его вход `rst_i` (через порт `counter_rst_o`) импульс сброса длительностью
ровно 1 такт. Если импульс был подан, при достижении N модуль на этом же
такте выставит `counter_code_valid_i = 1` вместе со случайным 16-битным
кодом на `counter_code_i`. Дождитесь этого события (`wait`) и запишите код и
`$time` в `counter_result_o` / `counter_timestamp_o`.

## Значения варианта

| Параметр | Значение |
| -------- | -------- |
| N (число тактов) | 31 |
| RESET_CYCLE (номер такта для импульса rst_i) | 11 |

## Требования к реализации

1. Выставить `counter_rst_o = 1` через `CLK_PERIOD/2` после фронта № 10, снять аналогично через 1 такт (после фронта № 11).
2. Дождаться `counter_code_valid_i == 1`.
3. Записать `counter_code_i` в `counter_result_o` и текущий `$time` в `counter_timestamp_o`.

# Блок 2. ПЗУ (ROM)

## Задание

Модуль `rom_dut` — комбинационная память. Требуется последовательно перебрать
все адреса (по одному адресу за такт) и просуммировать по модулю 65536 все
прочитанные значения `rom_data_i`.

## Значения варианта

| Параметр | Значение |
| -------- | -------- |
| DEPTH (число слов) | 28 |
| Разрядность адреса `rom_addr_o` | 5 бит |

## Требования к реализации

1. Перебрать адреса `0 .. 27` по одному за такт, выставляя новый адрес сразу после очередного фронта `clk`.
2. Суммировать все прочитанные `rom_data_i` по модулю 65536 (16-битное переполнение).
3. После обработки последнего адреса записать сумму в `rom_result_o` и `$time` в `rom_timestamp_o`.

# Блок 3. ОЗУ (RAM)

## Задание

Модуль `ram_dut` — модель памяти с 32-битной адресной шиной и 16-битными
данными. **Запись по адресу 0 модулем всегда игнорируется** — тест с
ADDR = 0 в таблице ниже обязателен и проверяет именно это. Нужно выполнить
все тесты по порядку (запись, затем чтение/проверка), после чего дождаться
случайного кода готовности.

## Значения варианта

| Параметр | Значение |
| -------- | -------- |
| ADDR[0] (обязательный: запись должна быть проигнорирована модулем) | 0x00000000 |
| DATA[0] | 0x0DBB |
| ADDR[1] | 0x0000643D |
| DATA[1] | 0xF161 |
| ADDR[2] | 0x00004146 |
| DATA[2] | 0x1D25 |
| ADDR[3] | 0x0000FBE9 |
| DATA[3] | 0xEF96 |
| ADDR[4] | 0x0000AE9F |
| DATA[4] | 0x32F1 |

## Требования к реализации

1. Выполнить тесты строго по порядку из таблицы. Каждый тест — 2 такта: на первом (через CLK_PERIOD / 2 после фронта) выставить `ram_we_o = 1`, `ram_addr_o`, `ram_data_o`; на втором снять `ram_we_o = 0`.
2. Дождаться `ram_done_valid_i == 1` (модуль выставит его после 4 успешных записей, не считая теста с ADDR = 0).
3. Записать `ram_done_code_i` в `ram_result_o` и `$time` в `ram_timestamp_o`.

# Блок 4. АЛУ (ALU)

## Задание

Модуль `alu_dut` — комбинационное АЛУ с фиксированной таблицей операций (см.
`blocks_dut.v`), его выходы `result_o`/`flag_o` можно использовать для
самопроверки, но они **не участвуют** в итоговой сверке. Параллельно на ту
же шину (`alu_op_o`, `alu_a_o`, `alu_b_o`) "смотрит" отдельный модуль
`alu_checker_dut`: он не вычисляет функцию АЛУ, а просто по порядку сверяет
предъявленные вами `op_i`/`a_i`/`b_i` с заранее заданной для вашего варианта
последовательностью тестов. Если очередной тест предъявлен верно (правильные
op/a/b, в правильном порядке), `alu_checker_dut` на этом же такте выставляет
`alu_code_valid_i = 1` вместе со случайным 16-битным кодом на
`alu_code_i` — этот код никак не связан с самой операцией и заранее не
публикуется, он появляется только по факту верного теста.

В вашем варианте нужно протестировать 2 операции — для каждой заданы
конкретные тестовые векторы (`a_i`, `b_i`). Нужно подать их по порядку и
просуммировать по модулю 65536 коды, которые выдаст `alu_checker_dut` за
каждый пройденный тест.

## Требования к реализации

1. Подать тестовые векторы обеих операций по порядку (сначала XOR, затем ADD), по одному тесту за 2 такта: на первом такте (через `CLK_PERIOD/2` после фронта) выставить `alu_op_o`, `alu_a_o`, `alu_b_o`; на втором такте дождаться `alu_code_valid_i == 1`.
2. Для каждого теста прибавить `alu_code_i` к накопительной сумме (по модулю 65536).
3. После обработки всех тестов обеих операций записать сумму в `alu_result_o` и `$time` в `alu_timestamp_o`.
